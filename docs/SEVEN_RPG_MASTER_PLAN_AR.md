## 0. الغرض والحدود

هذه الوثيقة هي المرجع التنفيذي الرئيسي لتطوير Seven RPG إلى لعبة RPG مستقلة، متماسكة، ذكية، قابلة للاختبار، ومصممة للهاتف أولًا. ليست Seven RPG مساعدًا عامًا أو مساعد برمجة أو حزمة إنتاجية. أي ميزة لا تحسّن تجربة لعب RPG أو موثوقيتها أو قابلية صيانتها تحتاج إلى مبرر واضح قبل إدخالها.

### قواعد غير قابلة للتفاوض
1. GitHub هو مصدر الحقيقة للكود والخطة والأدلة.
2. لا دمج إلى `main` ولا إصدار منشور ولا حذف ملفات/فروع دون موافقة المستخدم الصريحة.
3. لا حذف لقواعد البيانات أو ملفات الحفظ أو مفاتيح localStorage أو الاختبارات لتجاوز مشكلة.
4. الحفاظ على توافق البيانات الحالية؛ أي تغيير مخطط يتطلب ترحيلًا صريحًا واختبارات وسبيل رجوع.
5. لا إعادة كتابة الإطار أو نقل المشروع إلى تقنية جديدة لمجرد التفضيل. افحص البنية الفعلية أولًا.
6. كل ادعاء إنجاز مرتبط بدليل: أمر منفذ، نتيجة اختبار، SHA، سجل CI، لقطة شاشة أو سجل جهاز.
7. لا تخلط بين وجود ملف skill، واكتشاف الوكيل له، وتحميله، وتنفيذه بنجاح.
8. لا توضع مفاتيح API أو بيانات حساسة في المستودع أو السجلات أو اللقطات.
9. الوكلاء أدوات تنفيذ تحت المراجعة؛ مخرجاتهم غير موثوقة حتى يتم التحقق منها.
10. عند التعارض، تتقدم تعليمات المستخدم وعقد المنتج واختبارات المصدر الحالي على التقارير القديمة أو التخمين.

## 1. تعريف النجاح

يُعتبر Seven RPG جاهزًا للإصدار فقط عندما:
- يبدأ اللاعب قصة ذات معنى خلال ثلاث خطوات أو أقل.
- تؤثر قرارات اللاعب في الحالة والأحداث اللاحقة بصورة قابلة للتتبع.
- لا تعرف الشخصيات معلومات لم تصل إليها ضمن سياق العالم والقصة.
- تستمر الجلسة بعد الخروج القسري وإعادة الفتح دون فقد أو تلف.
- تستمر الحبكة والعلاقات والحقائق الأساسية خلال 20 دورًا على الأقل.
- تُكتشف تناقضات Canon وتُعرض معالجة آمنة لها بدل تجاهلها.
- تعمل الواجهة على الهاتف، بما في ذلك العربية RTL والوضع الليلي، دون قصّ أو تداخل.
- يكون الحفظ والاستيراد والتصدير والعودة من الخلفية مختبرًا على إصدارات Android المدعومة.
- تنجح الاختبارات الآلية وبوابات الإصدار، وتُرفق أدلة قابلة لإعادة الفحص.
- لا توجد مشكلة حرجة معروفة في البيانات أو الأمان أو مسار اللعب الأساسي.

هذه أهداف قبول وليست ادعاءً بأن الوضع الحالي يحققها. عقد RPG V2 الموجود في `.seven-team/cohesion/RPG_V2_PRODUCT_CONTRACT.md` هو مرجع المتطلبات التفصيلي ويجب إبقاؤه متزامنًا مع هذه الوثيقة.

## 2. تدقيق الحالة قبل التنفيذ

قبل أي تغيير إنتاجي:
1. افحص الفرع وSHA وحالة الشجرة والملفات غير الملتزم بها.
2. اقرأ `README`, `AGENTS.md`, عقد RPG V2، تقارير الحالة، ملفات المعمارية والملكية، الاختبارات وسير CI.
3. حدد نقطة الدخول الفعلية ونسخ الملفات القديمة/المكررة وما يستخدمه التطبيق فعلًا.
4. أنشئ مصفوفة: موجود، موصول بالمسار الفعلي، مختبر، مجتاز، غير مثبت، مفقود.
5. اربط كل ميزة بملفات التنفيذ والاختبار والدليل، ولا تعتبر تقرير تدقيق قديمًا إثباتًا للحالة الراهنة.
6. لا تبدأ إعادة كتابة كبيرة قبل تقرير الفجوات وموافقة المستخدم على تغييرات النطاق.

المخرجات المطلوبة: `docs/SEVEN_RPG_FEATURE_AUDIT.md`, سجل قرارات، قائمة مخاطر، وخطة مهام قابلة للتتبع.

## 3. المبادئ المعمارية

### 3.1 طبقات المسؤولية
- **واجهة اللاعب:** الشاشات، الإدخال، عرض السرد، الحالة، الوصولية، RTL.
- **Game Controller / Session Runtime:** تنسيق الدور، التحقق من المدخلات، حالة الجلسة، الإلغاء والأخطاء.
- **Game Systems:** العالم، الشخصيات، العلاقات، المهام، الفصائل، القتال، المهارات، المخزون والخريطة.
- **Canon & Knowledge:** الحقائق الثابتة، حقائق العالم المتغيرة، معرفة كل شخصية، ومصدر/زمن كل حقيقة.
- **Memory & Context:** ملخصات قابلة للتحقق، خيوط مفتوحة، استرجاع محدود الصلة، ميزانية سياق.
- **Model Runtime:** واجهة موحدة لمزودي النماذج، البث، الإلغاء، المهلات، التوجيه والتحويل الاحتياطي.
- **Tools / Search:** أدوات صريحة محدودة الصلاحيات مع تحقق من المدخلات والمخرجات.
- **Persistence:** مخطط بيانات بإصدارات، حفظ ذري قدر الإمكان، ترحيل، استيراد/تصدير، سجل أحداث.
- **Verification:** قواعد اللعبة، Canon، اتساق الحالة، سلامة المدخلات، اختبارات وتقييمات.

لا تُفرض مكتبة أو إطار جديد قبل إثبات الحاجة والتوافق. تُوثق الحدود والواجهات في `docs/SEVEN_RPG_ARCHITECTURE.md`.

### 3.2 مصدر الحقيقة والبيانات
- افصل Canon الثابت عن حالة العالم المتغيرة وعن معرفة الشخصيات وعن ملخصات السرد المشتقة.
- كل تغيير حالة مهم يحمل مصدرًا/سببًا وتوقيتًا/معرّف حدث مناسبًا لتشخيصه.
- لا تجعل نص النموذج وحده هو مصدر الحقيقة لقواعد اللعبة أو المخزون أو الصحة أو نتائج القتال.
- التغييرات المشتقة يجب أن تكون قابلة لإعادة البناء أو التحقق متى أمكن.
- لا تكتب حالة فارغة فوق بيانات غير قابلة للقراءة؛ أوقف العملية وأبلغ اللاعب مع حفظ نسخة احتياطية آمنة.

## 4. خارطة المراحل الرئيسية

كل مرحلة تبدأ بقراءة المصدر الحالي وتنتهي بأدلة قبول ومراجعة diff. المراحل قد تتداخل في التخطيط، لكن تغييرات الملفات المشتركة تُدمج بالتتابع.

### المرحلة 0 — التدقيق وتثبيت المتطلبات
- تدقيق المستودع ونقاط الدخول والنسخ القديمة.
- مراجعة عقد RPG V2 ومعايير RPG-01 إلى RPG-07.
- خريطة الميزات الموجودة/المفقودة/غير الموصولة/غير المختبرة.
- توثيق قرارات التقنية والملكية والتوافق.
**القبول:** لا توجد ادعاءات حالة غير موثقة؛ كل P0 له مالك وملف اختبار أو خطة تحقق.

### المرحلة 1 — أساس هندسي قابل للاستعادة
- تشغيل الاختبارات الحالية وتسجيل baseline.
- توحيد أو توثيق أوامر الاختبار والبناء دون إتلاف سير العمل الموجود.
- معالجة الأخطاء الحرجة التي تمنع التشغيل أو الاختبار.
- تعريف معالجة الأخطاء والإلغاء والمهلات والسجلات الآمنة.
**القبول:** تشغيل محلي قابل للتكرار؛ أخطاء CI مصنفة؛ لا حذف أو تجاوز لاختبارات لإنتاج نتيجة خضراء.

### المرحلة 2 — حالة اللعبة والحفظ والترحيل
- توثيق المخططات ومفاتيح التخزين والقراء والكتّاب.
- حفظ/استعادة العالم والجلسة والشخصيات والعلاقات والقرارات.
- ترحيل مخططات بإصدارات مع تحقق ونسخة احتياطية/تراجع.
- استيراد/تصدير العالم مع حدود الحجم والتحقق والتأكيد قبل الاستبدال.
- منع تلف البيانات من الاستبدال الصامت أو التزامن غير الآمن.
**القبول:** إنشاء، حفظ، force-stop، إعادة فتح، واستعادة صحيحة؛ اختبارات بيانات قديمة/تالفه/كبيرة/مكررة؛ لا فقد للبيانات.

### المرحلة 3 — نواة RPG والعالم
- تدفق إنشاء العالم والشخصية وبدء القصة.
- حالة الشخصيات وخصائصها ودوافعها وعلاقاتها.
- المهام والأحداث والاختيارات والنتائج.
- الفصائل والمواقع والخريطة والمخزون والمهارات والقتال حسب ترتيب الأولوية.
- قواعد حتمية للنتائج الميكانيكية؛ لا يُفوّض النموذج منفردًا تقرير قواعد اللعبة.
**القبول:** حلقة لعب قصيرة قابلة للإكمال؛ كل نظام مع اختبار حالة وواجهة واضحة؛ لا تبقى عناصر الواجهة شكلية بلا أثر محدد.

### المرحلة 4 — AI Runtime وCanon والذاكرة
- سياق لكل دور مبني على الحقائق ذات الصلة فقط.
- حجب المعرفة المستقبلية أو غير المثبتة عن الشخصيات.
- فصل تعليمات الراوي عن المعرفة التي يمكن مشاركتها داخل العالم.
- ملخص دوري وخيوط مفتوحة مع سقف محدد للسياق.
- تحقق من نتائج النموذج قبل اعتماد تغييرات الحالة.
- حفظ قرارات اللاعب ونتائجها وعلاقاتها بالأحداث.
**القبول:** اختبارات تسرب المعرفة، تناقضات Canon، أثر الاختيار، استمرارية 20 دورًا، واستمرارية بعد إعادة الفتح.

### المرحلة 5 — مزودو النماذج والأداء
- واجهة موحدة للمزودين مع تعريف قدرات كل نموذج من مصادر موثوقة.
- دعم الإعدادات/المزودين الموجودين بالفعل، وإضافة مزود جديد فقط بعد اختبار توافقه.
- بث الاستجابة، الإلغاء، المهلات، retry محدود، backoff، ورسائل خطأ قابلة للفهم.
- fallback عند الأعطال القابلة لإعادة المحاولة أو نفاد الحصة؛ لا fallback عشوائي عند خطأ بيانات/مصادقة دائم.
- إبقاء اختيار اللاعب واضحًا وإظهار المزود/النموذج الفعلي عند الحاجة.
- أسرار عبر إعدادات آمنة؛ لا مفاتيح مضمّنة في المصدر.
**القبول:** اختبارات انقطاع الشبكة، rate limit، timeout، auth، cancellation، streaming، وفشل كل مزود؛ لا حلقات fallback لا نهائية ولا وعود باستخدام مجاني غير محدود.

### المرحلة 6 — UI/UX وRTL والوضع الليلي
- تطبيق نظام تصميم موحد بدل تراكم استثناءات CSS.
- توحيد الألوان والخطوط والمسافات والأيقونات والحالات والمكونات.
- تحسين شاشة البداية، إنشاء العالم، غرفة اللعب، السجل، الشخصيات، الحقيبة، القتال والإعدادات.
- تصميم mobile-first لشاشات صغيرة ولوحة مفاتيح الهاتف ومناطق اللمس.
- العربية RTL، النص المختلط، الأرقام، الأسماء الطويلة، الحوارات والقوائم.
- وضع ليلي/نهاري متسق، تباين، focus، reduced motion وإمكانية الوصول.
- التقاط صور مرجعية بنفس أبعاد العرض واللغة والسمة ومقارنة الانحرافات.
**القبول:** لا تداخل/قصّ/تمرير أفقي غير مقصود؛ المسارات الأساسية قابلة للاستخدام بيد واحدة؛ مراجعة لقطات فعلية وليست تقديرًا نصيًا فقط.

### المرحلة 7 — الأمن والخصوصية
- فحص الأسرار والتبعيات والتراخيص والصلاحيات.
- التحقق من النصوص والملفات المستوردة وعناوين URL والمخرجات المعروضة.
- حماية WebView/bridges إن وجدت، وتقييد المكونات المصدّرة وصلاحيات Android.
- أقل قدر من السجلات اللازمة للتشخيص، دون مفاتيح أو محتوى خاص غير لازم.
- فصل محتوى المستخدم والمسترجع ومخرجات النموذج عن تعليمات الوكيل الموثوقة.
**القبول:** معالجة الثغرات الحرجة/العالية قبل الإصدار؛ توثيق الاستثناءات ومصدر التبعية وترخيصها؛ لا ادعاء شهادة أمنية رسمية.

### المرحلة 8 — الاختبارات وبوابات Android
- اختبارات وحدة وتكامل وواجهة ومسارات end-to-end.
- اختبارات create/save/import/export/force-stop/reopen.
- تحقق من SAF والأذونات على API 34 وAPI 36 أو الإصدارات الفعلية المدعومة.
- اختبار رجوع Android، استئناف التطبيق، لوحة المفاتيح، تدوير الشاشة حسب الدعم.
- لقطات شاشة وسجلات وأرقام build وSHA.
- التحقق من وجود APK وهوية الحزمة والتوقيع وSHA-256 بعد نجاح البناء والاختبارات.
**القبول:** نجاح بوابات CI واختبارات الجهاز المطلوبة مع أدلة قابلة لإعادة الفحص؛ لا اعتبار لاختبار المتصفح بديلًا عن Android.

### المرحلة 9 — الثبات والتوسع
- اختبارات جلسات طويلة، أحجام بيانات كبيرة، أخطاء مزود متكررة، وضع offline/شبكة ضعيفة.
- حدود للذاكرة والسياق والتزامن والمهلات.
- قياس زمن البدء وزمن أول استجابة وزمن الدور وحجم الذاكرة ومعدل الأعطال.
- تحسينات مبنية على القياس فقط.
**القبول:** لا أخطاء حرجة في سيناريوهات الثبات المحددة؛ قياسات قبل/بعد؛ لا تراجع في الحفظ أو جودة السرد.

### المرحلة 10 — توسيع RPG والإصدار
- توسيع الفصائل والعلاقات والمهام والأحداث والقتال والخريطة بعد ثبات الأساس.
- إضافة ميزات P2/P3 تدريجيًا من خلال vertical slices.
- مراجعة نهائية من وكيل مستقل ومراجعة تكامل.
- تحديث دليل المستخدم وسجل التغييرات وملاحظات الإصدار.
- إصدار مرشح RC مع تقرير كامل.
**القبول:** كل بوابات الإصدار خضراء؛ لا ثغرات حرجة أو فقد بيانات معروف؛ موافقة المستخدم قبل الدمج/النشر.

## 5. أولويات الميزات

### P0 — مانعة للإصدار
- بدء قصة موثوق وبسيط.
- حفظ واستعادة آمنان ومتوافقان.
- حماية Canon ومعرفة الشخصيات وحرية اللاعب.
- استمرارية القرارات والحالة.
- منع انهيار/تعليق مسار اللعب الأساسي.
- واجهة هاتف قابلة للاستخدام مع RTL والوضع الليلي.
- إعداد مزود النموذج وإظهار أخطائه بوضوح.
- اختبارات Android وCI قابلة للتحقق.

### P1 — أساسية للجودة
- محرر/منشئ عالم وشخصية أوضح.
- سجل أحداث وخيوط مفتوحة وملخص موثوق.
- استيراد/تصدير آمن.
- العلاقات والمهام والتقدم المستمر.
- مقارنة بصرية منظمة وإمكانية الوصول.
- fallback مضبوط ومقاييس زمن الاستجابة.

### P2 — توسع تجربة اللعب
- أنظمة قتال أكثر عمقًا، مهارات ومخزون.
- خريطة وفصائل وتفاعلات عالمية.
- أحداث متفرعة ونتائج طويلة المدى.
- أدوات اختبار وتقييم قصصية أكثر شمولًا.

### P3 — تحسينات مستقبلية
- محتوى إضافي وتأثيرات مرئية/صوتية عند ثبوت القيمة والأداء.
- أدوات تأليف ومراقبة متقدمة.
- تحسينات اختيارية لا تؤثر على سلامة المسار الأساسي.

كل ميزة جديدة تحتاج: وصف لاعب، سبب، نطاق، اعتماديات، حالة/بيانات متأثرة، مخاطر، اختبارات، ومعيار قبول. لا تُستخدم الأولويات كادعاء بأن الميزة موجودة.

## 6. مصفوفة القبول RPG-01 إلى RPG-07

| ID | معيار القبول | دليل الاختبار المطلوب |
|---|---|---|
| RPG-01 | بدء قصة ذات معنى في 3 خطوات أو أقل | اختبار مسار جديد مع تسجيل الخطوات |
| RPG-02 | خيارات اللاعب تؤثر على الأحداث اللاحقة | سيناريو متفرع يقارن حالة/حدث لاحق |
| RPG-03 | الشخصيات لا تعرف ما لم يصلها | اختبار حقائق future-knowledge وnot-established |
| RPG-04 | الجلسة تستمر بعد الخروج والعودة | حفظ ثم force-stop ثم إعادة فتح ومقارنة الحالة |
| RPG-05 | الاستمرارية خلال 20 دورًا | سيناريو ثابت متعدد الأدوار وفحص الحقائق والعلاقات |
| RPG-06 | اكتشاف تناقضات Canon ومعالجتها | حقن تناقض معروف والتحقق من تنبيه/حل آمن |
| RPG-07 | واجهة هاتف، RTL عربي ووضع ليلي | اختبارات viewport ولقطات RTL/dark/light |

## 7. الاختبارات المطلوبة

- Unit: قواعد اللعبة، تحويلات الحالة، migrations، التحقق من المدخلات.
- Integration: runtime + canon + persistence + provider adapter.
- E2E: بدء عالم، بدء قصة، قرار، نتيجة، حفظ، إعادة فتح، متابعة.
- Negative: JSON تالف، حصة منتهية، timeout، انقطاع الشبكة، استيراد مرفوض، معرفات مكررة.
- UI: شاشة صغيرة، نص عربي/مختلط، تكبير الخط، focus/keyboard، الوضع الليلي.
- Android: SAF، العودة/الاستئناف، force-stop، API 34/36 بحسب الدعم الفعلي.
- Visual: لقطات ذهبية قابلة للمقارنة مع viewport/theme/locale/build محدد.
- Release: artifact، package identity، signature، SHA-256، build SHA، CI.

يجب توثيق ما لم يُنفذ على أنه غير مختبر، لا نجاح ضمني.

## 8. نموذج عمل الوكلاء والمهارات

- الوكيل المخطط يقرأ هذه الوثيقة وعقد RPG ويقسم المهمة إلى وحدات قابلة للقبول.
- وكلاء الاختصاص يعملون على نطاقات/ملفات غير متعارضة قدر الإمكان.
- لا يملك أي وكيل صلاحية الدمج إلى main أو حذف بيانات/فروع أو نشر إصدار من تلقاء نفسه.
- كل handoff يذكر: الهدف، الملفات، التغييرات، الاختبارات والأوامر ونتائجها، SHA، المخاطر، والأسئلة المفتوحة.
- المراجع المستقل يراجع الامتثال للمتطلبات والأمان والتوافق والواجهة والاختبارات.
- المنسق يتحقق من الأدلة ويحل التعارضات ويحدّث سجل المهام.
- حد المحاولات: ثلاث محاولات إصلاح مختلفة جوهريًا ثم تقرير blocker بدل حلقة لا نهائية.
- المهارات لا تُعتبر مفعلة حتى يكتشفها runtime المناسب ويثبت ذلك باختبار بسيط.

راجع `.agents/skills/README.md` و`.agents/skills/SEVEN_RPG_SKILL_PACK.md` و`docs/SEVEN_RPG_AGENT_SKILLS.md` (إن وجد) لتفاصيل المهارات ومصادرها.

## 12. بوابة الإصدار النهائية

لا يُعلن الإصدار جاهزًا حتى:
1. جميع معايير P0 مجتازة بأدلة.
2. لا يوجد خلل حرج معروف في الحفظ أو Canon أو الأمان أو بدء القصة.
3. CI والاختبارات ذات الصلة ناجحة.
4. اختبارات Android الفعلية المطلوبة موثقة؛ لا يُستعاض عنها بفحص ثابت.
5. ملف APK والتوقيع والهوية والـ checksum متحققة.
6. مراجعة diff وتبعيات وأسرار مكتملة.
7. التقرير يذكر SHA والبيئة والأوامر والنتائج والفجوات المتبقية.
8. موافقة المستخدم الصريحة قبل الدمج إلى `main` أو النشر.
